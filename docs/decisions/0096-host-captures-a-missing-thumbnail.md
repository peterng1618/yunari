# 0096 — the host captures a missing thumbnail for a save it did not render

- **Date:** 2026-11-03
- **Status:** accepted
- **Paths:** `src/web/packages/host/src/panels/panel-manager.ts`,
  `src/web/packages/host/src/panels/panel-page.ts`,
  `src/web/packages/host/src/panels/panel-raster-browser.ts`,
  `src/web/packages/host/src/panels/panel-raster.ts`,
  `src/web/packages/host/src/panels/panel-capture.ts`,
  `src/web/packages/host/src/panels/panel-manager.fixtures.ts`,
  `src/web/packages/host/src/server/thumbnail-capture-route.ts`

## Problem

An editor save writes its own canvas capture to
`PUT /api/themes/:id/thumbnail`; the MCP server saves the same document but has
no canvas, so the library shows the theme's name until someone opens it in the
editor and saves again (#381). A second renderer in the MCP process would fail
quietly: Fabric needs a DOM, and a hand-built approximation would disagree with
the player about glass, charts and fonts.

## Rung 1 — internal owner

Searched: `createThumbnailStore`, `captureThumbnail`, `captureCanvas`,
`createPanelManager`, `capturePreview`, `servePanelPreview`, and
`panel-raster.ts`.

Found: `themes/thumbnails.ts` owns where a picture lives and what it accepts;
`editor/src/thumbnail-capture.ts` owns the authoring canvas capture;
`panels/panel-raster.ts` already renders the product's own player in a hidden
Chromium and `panel-manager.ts` owns the one shared browser. The missing piece
is a theme-only page URL and a capture that names no panel display.

## Rung 2 — installed dependencies

Searched: the host's dependency list, `sharp`, `canvas`, and the existing
Chromium/CDP rasteriser.

Found: no image library is installed, and none is needed to produce the PNG —
Chromium's compositor is the renderer. `node:zlib` is only the thumbnail
store's reader. Adding a Node canvas stack would rebuild the renderer, not reuse
it.

## Rung 3 — native platform

Searched: CDP `Emulation.setDeviceMetricsOverride`, `Page.navigate`,
`Page.startScreencast` and `Page.captureScreenshot`; Chromium headless window
behaviour (decision 0078).

Found: a target created with `newWindow: true` composites and screencasts at
any requested geometry, so the host can photograph a theme at thumbnail size
without a physical panel. The player's page needs no display record: `?theme=`
is the same call `preview_theme` already hands an agent.

## Rung 4 — public solutions

Searched: Puppeteer `page.screenshot`, Playwright `page.screenshot`, and
server-side canvas (`node-canvas`, `sharp`) rendering; also how comparable
theme galleries generate previews.

Found: both automation libraries would produce the picture, but each adds a
second browser download and its page API creates hidden tabs unless the window
option is used (probe in 0078). `sharp` and `node-canvas` cannot render Fabric or
ECharts without reimplementing them. The gallery convention is a preview
generated by the same renderer that displays the product.

## Rung 5 — integration comparison

| Option | Fit | Unsolved work | Verdict |
|---|---|---|---|
| MCP renders the document | No DOM | A second renderer kept in step by hand | Rejected: silent divergence |
| MCP returns a URL for the user to capture | Honest | The issue's premise — no picture until a human acts | Rejected: does not fix it |
| Host photographs the player page | Same renderer as a display | No display record; page at thumbnail geometry | **Chosen** |
| Host renders a panel preview | Reuses `capturePreview` | Needs a configured panel and its geometry | Rejected: most libraries have no panel |
| Add Puppeteer/`sharp` | Works | New dependency, second browser or a partial renderer | Rejected: dependency cost |

## Rung 6 — smallest probe

A built host was started with the circle-theme fixture and the player opened at
`/?theme=circle-probe&panel=1` in a 640x640 Chromium window. The mounted canvas
was 640x640, the console stayed empty, and the screenshot showed the themed disc
with no page chrome. Without `panel=1` the same page drew a "Connecting to the
host" bar across the bottom, so the capture URL carries `panel=1`.

A second probe captured through the route itself: the first frame of a
screencast was the blank page before the theme painted, while
`Page.captureScreenshot` after the player's `data-yunari-live` marker produced
the themed disc. The one-shot path therefore waits for that marker and for the
background layer's own image (bounded to 6 s) and photographs the page; it never
starts a screencast.

## Decision

The panel manager gains `captureTheme(themeId, geometry)`, which uses the one
shared raster browser to photograph the player's theme-only page and closes the
target; `pageForTheme` supplies that URL (`?theme=<id>&panel=1`). A loopback
`POST /api/themes/:id/thumbnail/capture` computes a 640-long-edge geometry from
the stored artboard and writes the PNG through the thumbnail store. It refuses
without overwriting when a picture already exists, so an editor capture is never
replaced by a coarser player render. `save_theme` asks for the capture after its
save and reports whether one was produced.

The MCP save still succeeds when capture fails — no browser, shutdown, a theme
that vanished — because the document is stored and the absence is reported
rather than invented.

A circle theme's picture is the square player page with the disc inside it; the
editor's own capture clips to the disc. Cropping here would need a PNG
transform the host has no owner for, so the square is kept. Upgrade path: give
the capture-only page a transparent backdrop and photograph it with
`omitBackground`, which the player's overlay mode already proves is possible.
